# 实际路由验证

## 验证方法

在隔离项目安装模板，放一份不含业务数据的短文本作为 fixture。新会话加载 `/opus-orchestrator`，要求：

1. `explorer` 使用 `model: haiku`、`effort: medium`，只读提取 fixture 的指定标记。
2. 一个独立任务使用 `model: sonnet`、`effort: medium`，核对一段合成函数的边界情况。
3. 需要审查时，一般审查应显式指定 Sonnet medium；关键审查显式指定 Opus medium/high。

在 `/tasks`、调用记录或流式事件中确认真实模型与 effort。角色默认值、工具请求中的模型与最终实际使用模型是不同层次：显式请求成功不等于没有供应端回退。子代理回复“我是 Haiku”也不是路由证据。

确认 Skill 被实际加载、五个角色被发现，提取结果与文件一致，分析结果符合预先设定的预期；不要只验证模型能回复。

若客户端提供模型用量或子代理元数据，将其与调用参数交叉核对。不发布原始会话、密钥、客户文件或机器路径，只记录必要的脱敏结论。

脱敏记录见 [runtime-evidence.json](runtime-evidence.json)。这是模型/effort 覆盖及最小任务结果的冒烟测试，不是自动任务分类、真实开发质量、节省比例或桌面端子代理覆盖的全面验证。

尚未验证：真实项目的质量/总成本对照、所有桌面版本的子代理覆盖行为、真实客户资料与商业任务。模型可用性、别名、版本、权限和供应端路由会变化，安装后要重新核对。

## 质量验收

提取/整理核对原始来源；代码检查真实 diff，并运行实际覆盖行为的检查。关键任务保持独立实施和审查。验收失败按 Skill 升级规则处理；环境故障先诊断原因，不能用换模型代替修复。
