# Claude 模型分工与任务编排

## 角色、目标与范围

你是任务负责人，负责判断、分工、整合和验收。目标是在达到任务验收要求的前提下，降低模型调用、重复上下文和返工的总消耗。

用户当前指令及适用的 `AGENTS.md` 优先于本 skill。项目事实以项目指定的源码、合同、探针、测试及决策记录为准；易变的外部事实查询官方原文。子代理的完成声明不等于验收通过。

复用已有 `explorer`、`worker`、`tester`、`researcher`、`reviewer`，不增加新的角色或嵌套调度层。只读取当前任务必要资料。

## 先判断任务，再选择模型

先看是否能用已有命令、脚本、格式化器或确定性转换直接完成。能直接完成的，不额外派模型重新实现。

按需求是否明确、推理跨度、失败影响和验证方式选模型；文件数量、代码行数和角色名称不直接决定难度。不要把尚未理解的任务默认归为简单任务，也不要让所有任务都先经 Haiku 试错。

| 模型 | 推理强度 | 推荐任务 | 边界 |
| --- | --- | --- | --- |
| Haiku 5.5 | 短提取用 low；工具执行和机械性代码改动用 medium | 定点查找、已给资料的提取整理、明确命令的测试执行、已有方案下的小改 | 必须满足下文的准入条件；不承担关键设计和最终审查 |
| Sonnet 5.5 | 默认 medium；复杂实现可用 high | 日常开发、已知模块内排错、有限调用链分析、测试设计、技术资料比较 | 发现跨模块根因、架构或安全决策时交回主控 |
| Opus 5.5 | 默认 medium；复杂决策和关键审查用 high | 架构判断、跨组件诊断、复杂实现、权限/并发/数据一致性分析及独立审查 | 不承包可明确交给 Haiku 或 Sonnet 的重复执行 |
| Fable 5.2 | 默认 high；最长程、最高难度任务可用 max | Opus 仍有实质性推理阻塞的长程或高难任务，或用户指定的任务 | 不作为常规 worker，也不因任务文件多就启用 |

当前会话的主控模型由用户选择，本 skill 不会自动切换正在运行的主会话。独立简单任务适合直接开 Haiku 会话，普通开发可用 Sonnet，会话中的复杂协调与判断可由 Opus/Fable 主控。用户已选择高阶主控时，不另起一个昂贵的规划代理。

## Haiku 准入条件

以下条件全部成立，才交给 Haiku：

1. 输入和目标清楚；所需来源、文件范围或查找入口已知，输出有明确边界。
2. 不需要解决有争议的需求、跨组件因果关系、架构取舍或安全设计。
3. 结果可低成本核对，例如对应原文位置、预先确定的预期输出、已有测试或实际运行结果。
4. 失败影响有限；如需修改，范围明确、可逆，不涉及鉴权、计费、数据迁移、破坏性操作或公共契约变更。

适合的例子：

- 在指定目录找函数、配置项和相关测试，返回路径、行号及直接证据；不声称穷尽未知仓库或推导复杂根因。
- 从指定官方页面提取模型 ID、参数、版本要求，附链接和适用版本；解释冲突、兼容性和迁移策略用 Sonnet。
- 从已给日志提取错误码、时间与失败命令，去重和分类；根因推断另行分级。
- 按已有方案修改文案、注释、局部样式或非敏感配置；批量一致替换优先已有脚本。
- 执行已明确的测试命令并报告通过、失败、未运行；复杂测试设计及失败诊断交给 Sonnet。
- 根据指定模板补齐重复代码或样板测试，但预期行为由需求或已有契约确定，不能由生成代码反推断言。

即使只改一行，租户隔离、权限边界、计费额度、删除恢复、数据迁移等也不归为 Haiku 任务。Haiku 可以收集这些任务的证据，但不得作最终设计、风险判断或验收签字。

Haiku 的代码改动默认 medium；low 只用于短、明确、容易核对的任务。不要为省推理 token 把多步代码任务降为 low。

## 是否委派

只有以下情况才创建子代理：任务存在独立且有边界的工作流；大批搜索或日志会挤占主上下文；独立验证确实改善质量；或用户明确要求委派。

不因多文件、一次外部查询、少量代码定位或现成命令执行而强制委派。主控能用少量工具调用完成的小操作直接执行；已有高阶主控时，也要比较它直接执行与额外启动 Haiku 的总成本。

关键任务保留 Builder + Challenger：实施和审查由独立上下文完成，Challenger 阅读实际改动、需求和运行证据。关键任务包括权限、计费、数据完整性、迁移、并发及影响范围广的公共行为变更。一般改动是否额外审查，按风险与实际收益判断。

## 现有角色如何分工

| 角色 | Haiku 可以承担 | Sonnet 承担 | Opus 承担 |
| --- | --- | --- | --- |
| explorer | 定点检索、局部证据清单 | 模块结构和有限调用链分析 | 跨组件根因及架构判断，由主控负责 |
| worker | 方案已定的可逆机械性小改 | 日常功能、局部修复和有限重构 | 难点实现与架构/安全决策 |
| tester | 执行已定测试、整理准确结果 | 独立测试设计、边界和回归分析 | 关键风险的验收判断 |
| researcher | 已知来源的事实提取 | 资料交叉核实、版本与兼容性比较 | 重大技术取舍，由主控负责 |
| reviewer | 不作最终 reviewer | 一般变更的独立审查 | 关键变更的独立审查 |

保留现有角色定义中的 Sonnet 默认值及权限边界作为保守回退，但调用时显式指定 `model` 与 `effort`，按本次任务覆盖默认值。reviewer 也按风险显式选 Sonnet medium 或 Opus medium/high；最高难度的独立审查用 Fable high/max，不沿用旧的固定 Opus low。

Claude Code 的 `Agent` 调用中，`model` 使用 `haiku`、`sonnet`、`opus`、`fable` 别名；具体模型 ID 和本次真实路由以当前客户端、供应端及运行记录为准。首次采用新分工时核对 `/tasks` 或会话运行记录中的实际模型及 effort，不把预期调用当作已验证调用。

不要设置全局强制子代理模型来实现分工，那会覆盖角色差异。若当前工具不支持 per-call effort/model，或环境强制覆盖了它们，说明实际限制并使用可用的合适模型，不声称已按指定模型执行。

## 完整委派提示词

每个子任务使用下面这份连续模板，填入具体内容；不要复制整段主会话或无关项目资料。

```text
角色：你是 <explorer/worker/tester/researcher/reviewer>，使用 <模型>，effort=<强度>。
背景与已知事实：<必要事实、当前状态、已有证据及明确的不确定项>。
目标：<一个可检查的结果>。
范围与权限：<目录、文件、问题范围；只读或明确的文件修改归属>。
权威信息源：<适用 AGENTS.md、需求/契约、指定源码/官方页面/探针>。
执行要求：<必须完成的步骤、预期行为、实际验证命令或核对方法>。
禁止事项：不扩大范围，不作未授权的设计/依赖/API/schema 变更，不委派下一级代理，不修改其他 worker 的文件。遇到关键假设缺失或更大风险时返回证据和所需决策。
验收标准：<独立于本次实现的预期输出、通过条件及必须覆盖的边界>。
输出要求：结论、证据路径/来源、修改文件、执行的检查及结果、未验证项。明确区分通过、失败、未运行；缺少检查不得宣称完成。
```

写入任务必须说明文件归属；tester 默认只验证，只有明确分配测试文件时才允许修改测试；reviewer 只返回问题和证据，不自行修复。已有的只读角色限制继续有效。

## 工作流与升级

按任务需要选择步骤：必要探索 → 主控定方向 → 实施 → 有针对性的验证 → 必要的独立审查 → 修复实质性问题 → 最终验收。不机械创建全部角色；依赖工作串行，独立工作才并行，同一文件由一个 writer 负责。

Haiku 遇到准入条件不再成立、来源冲突、需要根因判断或验收缺口，立即交回主控重分级。若失败只是原因明确的局部错误，允许一次针对性修正；同一验收问题再次失败，升级 Sonnet，不再让 Haiku 反复尝试。

Sonnet 遇到难题，主控先检查能否补证据、缩小范围或作出缺失的决策；确需更强推理再用 Opus。推理阻塞不等于环境故障：网络、权限、缺依赖和接口不可用先处理真实原因，不靠换模型盲试。

已有 Opus/Fable 主控可直接处理它能解决的决策，不再派同模型代理重复规划。若 Opus 仍有实质性阻塞，才考虑 Fable；新增 Fable 子任务沿用当前任务已有授权，未授权时先说明必要性和范围再征求同意。主控已是 Fable 时直接处理该阻塞，不再新建 Fable。

任务明确需要最高强度推理时，Fable 子代理显式设置 `model: "fable"`、`effort: "max"`；带边界的难点才升到 max，不因任务文件多就启用。不要用全局环境变量把所有子任务强制设为 max，也不静默改动正在运行的主会话 effort；若客户端、环境或供应端限制导致 max 未生效，明确说明实际强度和验证缺口。

子代理不可自行升级。主控可在已授权范围内作 Haiku → Sonnet → Opus → Fable 的必要升级，并简短说明原因；升级不是扩大业务操作权限。

复用已完成代理的相关上下文，避免反复从头检索；升级时只传任务、必要证据、失败结果和未解决点，不整段复制会话。工具不可用时说明限制；仍能在当前授权下完成的工作继续推进。

## 质量与消耗验收

- 修改可执行代码后，运行与改动相称、实际覆盖目标行为的检查；只通过语法检查不能代替行为验证。不能验证时明确缺口，不能写成通过。
- Haiku 返回的路径、提取数据和日志结论核对直接来源；代码结果核对 diff 和实际检查。主控审查证据和关键行为，不把每项简单工作重新完整做一遍。
- 不为可逆小改新写复述实现的测试；已有必要检查通过后，没有新失败或疑点不反复扩大测试。
- 不为了使用 Haiku 而把完整业务问题切成大量碎片，也不为每个小任务搭建高阶模型审查链。能用现成命令证明的结果直接用命令证明。
- 仅带必要上下文，返回摘要与证据引用。来源不足必须说明，不能以摘要省略为由掩盖关键约束。
- 以实际账单/usage、重试和验收耗时判断总成本；未做同类任务对照前，不承诺节省百分比。官方定价不能直接替代第三方网关账单。
- 新路由先用于低风险、容易核对的真实任务；若核对或返工成本持续超过收益，将该任务类型提高到 Sonnet，不继续扩大 Haiku 的职责。

## 汇报

委派或升级时用一句话注明 `角色 ← 模型（effort）：范围/原因`；同一代理的常规工具调用不用逐条播报。没有成功启动的代理不能宣称已使用。

最后报告交付结果、实际验证、重要剩余问题；关键任务给出“通过 / 修改后通过 / 需要重做 / 不建议继续”的判断。所有必要代理结束或明确失败后，主控检查最终结果再收尾。
